
# PROJECT: STANDALONE MULTI-MODEL LLM TESTING WORKBENCH

You are tasked with designing and implementing a standalone application for conducting repeatable, large-scale experiments with Large Language Models.

This is a full application development project, not a request for an architectural proposal or a proof-of-concept document.

Build a functional application, implement its core features, test its operation, and provide clear instructions for running it.

The application will be part of the broader AnansiForge creative ecosystem, but it must operate independently of AnansiForge.

Do not begin by modifying AnansiForge or attempting to integrate the application into its existing interface.

Read this specification completely before beginning implementation.

==================================================
1. FUNDAMENTAL PURPOSE
==================================================

The application is a test-agnostic LLM experimentation workbench.

Its primary function is to:

1. Accept a Personality.
2. Accept a Scenario.
3. Accept an Initial Message.
4. Accept a predefined user response.
5. Submit that conversation to one or more configured LLMs.
6. Generate a configurable number of independent responses from each LLM.
7. Store every response and its execution metadata.
8. Present the results in an organized, searchable interface.
9. Allow the user to record observations using customizable data fields.
10. Generate graphs and comparisons from the recorded data.

The application must not assume what the user is testing.

Possible experiments include:

- Character voicing consistency.
- Character behavior.
- Narrative continuity.
- Instruction adherence.
- Dynamic narrative outcome mechanics.
- Player-agency preservation.
- Ensemble character participation.
- Differences between LLMs.
- Differences between versions of the same prompt.

These are examples of user-defined experiments, NOT features requiring specialized implementations.

The application must not contain hardcoded evaluation logic for any of these topics.

A character voicing experiment and a combat resolution experiment must use the same underlying execution engine.

The user defines what is being tested and what information should be recorded.

The application handles execution, organization, storage, searching, and visualization.

4. EXPERIMENT HIERARCHY
==================================================

The application must support the following hierarchy:

EXPERIMENT
    EXECUTION RUN
        SUBTEST
            TEST CASE
                MODEL
                    ITERATION
                        RESPONSE
                        TEST RECORD

An Experiment is the reusable definition.

An Execution Run is a historical snapshot of one execution of that definition.

A Subtest organizes related test cases.

A Test Case contains a specific user response and its effective prompt configuration.

A Model represents a selected API model.

An Iteration is one independent generation.

A Response contains the actual generated output.

A Test Record contains the user's recorded observations.

These entities must remain logically distinct.

- Reordering subtests.
- Disabling subtests.

Bulk creation is important.

A user may want to test 180 characters under the same general conditions.

The application must not require manually constructing 180 nearly identical configurations.

==================================================
9. PROMPT CONSTRUCTION
==================================================

The application must construct a conversation containing:

1. The bot's configured Personality and Scenario.
2. The bot's Initial Message.
3. The predefined user response.

The Initial Message must be represented as an assistant message.

The predefined response must be represented as a user message.

Personality and Scenario should be placed in appropriate instruction fields or message roles supported by the provider.

Make prompt formatting explicit and inspectable.

Do not silently introduce unrelated instructions or modify the author's original content.

Some provider APIs use different message-role structures.

The provider adapter is responsible for handling those differences.

Store the effective prompt and relevant request parameters with each execution.

Preserve literal placeholders such as {{User}}.

If placeholder substitution is supported, it must be explicitly configured.

Do not accidentally process roleplay placeholders as application template syntax.

==================================================
10. BATCH EXECUTION
==================================================

For the initial implementation, every iteration must be an independent, fresh conversation.

Example:

Personality + Scenario
Initial Message
User Response
Generate Response

Save the response.

Reset to the original conversation.

Repeat.

The previous iteration's generated response must NOT be included in the next iteration's context.

This is essential for measuring variation across independent generations.

The default execution order should be:

Experiment
    Subtest
        Test Case
            Model
                All repetitions

Complete all configured repetitions for each selected model before advancing to the next test case.

This keeps related results together.

The application should allow completed results to be reviewed while subsequent jobs continue executing.

Persistent multi-turn testing may be added later as a separate execution mode.

Do not accidentally turn single-response repetitions into continuing conversations.

==================================================
11. THROTTLING AND RATE LIMITS
==================================================

The application must support controlled request pacing.

Provide configurable:

- Minimum interval between requests.
- Maximum simultaneous requests.
- Per-provider concurrency limits.
- Per-provider request intervals.
- Request timeouts.
- Retry limits.
- Retry backoff.

Default to conservative settings.

Prefer reliability over maximum throughput.

Respect provider rate limits and retry-after information where available.

Do not attempt to evade provider restrictions.

A provider failure should not unnecessarily terminate an entire experiment.

Record the failure and continue with other eligible jobs.

Distinguish unsuccessful API requests from valid generated responses.

==================================================
12. PERSISTENT EXECUTION QUEUE
==================================================

Large experiments may require many hours.

Implement a persistent job queue that survives application restarts.

Save each successful response immediately.

Do not hold all responses in memory until the batch finishes.

Support the following controls:

START
PAUSE
RESUME
CANCEL REMAINING JOBS
RETRY FAILED JOBS

Pausing should prevent new requests from starting while allowing active requests to complete safely.

Resuming must continue the existing run.

Completed jobs must not be regenerated automatically.

If the application crashes during a request, preserve the attempt's status accurately.

Do not assume a request failed merely because its response was not saved.

Provide a mechanism for recovering uncertain jobs.

The execution interface should display:

- Total jobs.
- Completed jobs.
- Pending jobs.
- Active jobs.
- Failed jobs.
- Current subtest.
- Current model.
- Current repetition.
- Elapsed time.
- Approximate remaining time, when meaningful.

Where supported, record token usage and provider-reported costs.

Allow configurable limits to help prevent unintended API spending.

==================================================
13. IMMUTABLE EXECUTION HISTORY
==================================================

This is a critical requirement.

A reusable Experiment Definition must be separate from an Execution Run.

Every execution creates a new Run ID.

Snapshot the exact configuration used for that run.

This includes:

- Experiment metadata.
- Selected subtests.
- Test cases.
- Effective Personality.
- Effective Scenario.
- Effective Initial Message.
- Predefined user responses.
- Model selections.
- Generation parameters.
- Test Record Sheet schema.
- Source asset references and relevant content hashes.

Editing the reusable experiment must not change any historical run.

Rerunning an experiment must never overwrite previous results.

Example:

Introduction Test
    Run 001: Original personalities
    Run 002: Revised personalities
    Run 003: Updated model configuration

All runs remain independently accessible.

Clearly distinguish:

RUN:
Create a new execution.

RERUN:
Create a new execution from an existing test definition.

RESUME:
Continue an interrupted execution.

RETRY:
Attempt to complete a failed job in its existing execution.

Historical raw responses must never be silently replaced.

15. DEBUG TRACKER PRESET
==================================================

Include an optional setting labeled:

"Enable / Disable Debug Tracker for Scenario"

This setting is only a convenience feature for configuring recording fields.

When enabled, it adds predefined, editable debug-related fields to the Test Record Sheet.

It does NOT:

- Modify the Scenario.
- Insert instructions into prompts.
- Automatically detect debug headers.
- Parse model responses.
- Evaluate model behavior.
- Mark responses as successful or unsuccessful.

The user is responsible for any debug instructions in the Scenario.

The user is also responsible for reviewing the model's output and entering the relevant observations.

A model's self-reported debug information is not authoritative evidence of successful behavior.

The Test Record Sheet remains the place where observations are recorded.

21. SECURITY AND DATA INTEGRITY
==================================================

Store API credentials securely.

Never include credentials in logs, exported experiments, or response records.

Only send the configured prompt content to the selected provider.

Do not transmit unrelated Vault assets or historical test data.

Treat imported files and model responses as untrusted content.

Never execute instructions contained in a model response as application commands.

Never permit generated text to modify credentials, files, experiment configurations, or execution settings.

Preserve the original response text exactly as received.

Separate raw evidence from user-entered evaluation data.

Ensure database operations are safe during concurrent execution and review.

Use transactions where appropriate.

23. AUTOMATED ACCEPTANCE TESTS
==================================================

Implement mock model providers so the application can be tested without consuming paid API credits.

At minimum, verify the following scenarios.

TEST A: BATCH COUNT

Create an experiment containing:

2 test cases.
3 models.
5 repetitions.

Verify that exactly 30 successful responses are generated and stored.

TEST B: INDEPENDENT CONTEXT

Verify that every repetition receives the same initial configured conversation.

Previous generated responses must not appear in subsequent repetitions.

TEST C: CONFIGURATION INHERITANCE

Override Personality for one subtest.

Verify that only that subtest uses the override.

TEST D: HISTORICAL PRESERVATION

Execute an experiment.

Modify its Scenario.

Execute it again.

Verify that both runs retain their original configurations and results.

TEST E: INTERRUPTION AND RECOVERY

Interrupt a batch after several responses have been saved.

Restart the worker.

Verify that the existing run resumes without discarding or duplicating completed responses.

TEST F: PROVIDER FAILURE

Simulate timeouts, authentication failures, and rate limits.

Verify correct error recording, retries, and continuation of unrelated jobs.

TEST G: RECORDING FIELDS

Create custom fields and enter review data.

Verify that results remain associated with the correct fields after editing display names.

TEST H: VISUALIZATION

Enter categorical and numeric review data.

Verify that appropriate graphs are produced.

Verify that graphs exclude unreviewed observations from reviewed-only statistics.

TEST I: VAULT COMPATIBILITY

Using representative AnansiForge fixtures, verify correct import into Personality, Scenario, and Initial Message.

Verify that original source files remain unchanged.

TEST J: LARGE-BATCH PREPARATION

Construct an experiment with 180 subtests, 5 mock models, and 25 repetitions.

Verify that the application correctly creates and counts 22,500 generation jobs.

Verify that the queue, database, and interface can handle the workload without requiring all jobs or responses to remain in memory.
